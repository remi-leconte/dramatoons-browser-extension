# Dramatoons : extension navigateur

Extension « Dramatoons Highlighter », commune à Firefox et aux navigateurs Chromium (Chrome, Edge) : un seul code et un seul manifeste (Manifest V3). JavaScript sans framework ni étape de construction. Règles métier : `extension.md` du skill `regles-metier` (workspace).

Elle remplace les anciennes extensions `dramatoons-extension-firefox` et `dramatoons-extension-chromium` (version 2.x), gardées telles quelles jusqu'à sa publication. Elle reprend l'identifiant Firefox de l'ancienne (`browser_specific_settings.gecko.id`), qui ne doit jamais changer : c'est lui qui fait de chaque version une mise à jour de la fiche du store de Mozilla. Sa version suit celle du site (`2.5.0` pour la v2.5.0), et doit rester supérieure aux versions déjà publiées sur les stores.

## Commandes
Node n'est pas installé sur le poste : les commandes tournent dans le conteneur `node` de `compose.yaml`. Depuis `extension/` :

```sh
docker compose run --rm node npm ci        # installe les dépendances (node_modules/)
docker compose run --rm node npm run ci    # vérifications de la CI (voir « CI »)
docker compose run --rm node npm test      # tests Vitest
```

## Organisation
Convention des fichiers JS de `src/`, vérifiée par la CI :
- un **module** (`import`, `export`, `await` hors fonction) porte l'extension `.mjs`, y compris un fichier seulement importé par un autre ; une page HTML le charge par `<script type="module">` ;
- un **script classique** porte l'extension `.js` : scripts de contenu (le navigateur les charge toujours ainsi) et scripts chargés par `<script>` sans `type` ;
- seule exception : l'arrière-plan déclaré `"type": "module"` dans le manifeste est un module, même en `.js`.

Un `.mjs` déclaré en script de contenu (dans le manifeste ou dans `lib/scripts-injectes.mjs`, la liste des scripts que l'arrière-plan injecte), ou en arrière-plan sans `"type": "module"`, fait échouer la CI, comme un script injecté absent.

- `src/` : l'extension telle qu'elle est chargée par le navigateur, `manifest.json` à la racine. Seul ce dossier est livré.
  - `manifest.json` : l'arrière-plan est déclaré pour les deux navigateurs, `service_worker` pour Chrome et Edge, `scripts` pour Firefox ; chacun ignore la clé de l'autre. Permissions : `storage`, `scripting` (injection du surlignage), l'accès à tous les sites (`<all_urls>`, pour surligner n'importe quelle page) et, nommément, à l'API de production et à celle du dev (`127.0.0.1:8081`). L'API reste nommée malgré `<all_urls>`, pour que l'accès à l'API survive au retrait de l'accès aux sites quand le navigateur distingue les deux (Firefox). Sur Chrome et Edge, le réglage « au clic » peut retenir aussi l'API : la fenêtre vérifie donc l'accès aux sites avant tout appel, et propose de le rendre même quand l'API est injoignable ou que l'utilisateur est déconnecté. Déclaration de collecte de données pour Firefox (`data_collection_permissions`) : `authenticationInfo`, car l'extension transmet le login et le mot de passe à l'API de Dramatoons et en garde les jetons ; elle ne transmet rien d'autre, et rien à un tiers.
  - `config.mjs` : `API_URL`, versionné avec l'adresse de l'API du dev (voir la construction du zip, ci-dessous).
  - `background.mjs` : l'arrière-plan, seul à appeler l'API. Il répond aux messages de la fenêtre (`chrome.runtime.sendMessage({ type, … })`, réponse `{ ok, resultat }` ou `{ ok: false, erreur }`) : `connexion`, `deconnexion`, `utilisateur`, `etatOnglet`, `changerOnglet` et `rafraichir` (tous deux répondent `{ actif }`, ou `{ actif: false, deconnecte: true }` si la session a expiré). Il ignore les messages d'une autre extension et ceux qui viennent d'un onglet : le script de contenu tourne dans des pages tierces, seule la fenêtre pilote l'arrière-plan. Conséquence : une page de l'extension ouverte dans un onglet (une future page d'options, par exemple) ne pourrait rien commander sans adapter ce contrôle.
    - Activation d'un onglet : il charge la liste (`GET /webtoons?mode=ext&pagination=false`), la garde pour l'onglet, injecte `lib/correspondance.js` et `contenu.js` (`chrome.scripting.executeScript`), puis envoie la liste à la page (`{ type: 'surligner', liste }`). À chaque page chargée dans un onglet activé (`tabs.onUpdated`, `status: 'complete'`), il réinjecte avec la liste gardée, sans appel à l'API, et seulement si la session existe encore (une session expirée ne surligne plus rien jusqu'à la reconnexion). Dans un onglet qui n'est plus activé (ou sans session) mais qui a déjà été surligné (marque `surligne-<id>`, gardée jusqu'à la fermeture de l'onglet), chaque page chargée reçoit `{ type: 'retirer' }`, sans injection ni appel à l'API : une page revenue du cache de navigation (« Précédent ») ne garde pas l'ancienne liste. Un onglet désactivé ne reçoit aucun script. Une page où l'extension ne peut pas s'exécuter (page interne du navigateur, store) n'est simplement pas surlignée. Une désactivation, une déconnexion ou la fermeture de l'onglet arrivée pendant une activation l'emporte sur elle, grâce à un numéro de demande par onglet :
      - après le chargement de la liste, l'activation vérifie que le numéro n'a pas changé, puis prend le sien : un chargement en erreur ne change rien, et n'annule donc pas le surlignage d'une page en cours ;
      - après l'enregistrement de l'onglet activé, elle le compare de nouveau, et annule cet enregistrement si une désactivation ou une déconnexion est passée sans le voir ;
      - juste avant d'envoyer la liste à la page, il est comparé en dernier, sans attente avant l'envoi : un « retirer » envoyé pendant l'injection a pu se perdre avant que la page écoute.
  - `lib/session.mjs` : connexion (`POST /login`), jetons dans `storage.local` (gardés à la fermeture du navigateur), requêtes authentifiées avec un seul renouvellement à la fois (`/token/refresh`, jeton à usage unique), déconnexion si le renouvellement est refusé ou ne renvoie pas de nouveau `refresh_token` (pas sur une panne réseau, une API en erreur, 5xx, ni un délai dépassé). Toute fin de session, demandée ou due au renouvellement, appelle l'action enregistrée par l'arrière-plan (`surDeconnexion`), qui retire le surlignage de tous les onglets activés, les désactive et oublie leurs listes : la liste d'un utilisateur ne sert jamais à un autre. Chaque appel à l'API a un délai maximal de 10 secondes (`DELAI_API_MS`), au-delà duquel il échoue comme une panne réseau.
  - `lib/onglets.mjs` : état de l'interrupteur, liste et marque « déjà surligné » de chaque onglet, dans `storage.session`, qui survit à la mise en veille de l'arrière-plan de Chrome. L'état et la liste sont oubliés à la désactivation et à la fermeture de l'onglet ; la marque seulement à la fermeture, pour qu'une page revenue du cache (« Précédent ») reçoive encore « retirer ».
  - `lib/scripts-injectes.mjs` : la liste des scripts que l'arrière-plan injecte dans un onglet activé, lue aussi par `scripts/verifier.mjs`.
  - `lib/liste.mjs` : réduit la réponse de l'API à ce que le surlignage utilise (titres sans doublon, état, note, chapitre ; un chapitre 0 est absent).
  - `lib/correspondance.js` : correspondance des titres (règles « surlignage » 1 à 6) : texte normalisé (sans casse, accents ni ponctuation) avec la position de chaque caractère dans le texte d'origine, mots entiers ; titres tronqués cherchés d'abord, devant chaque « … » ou « ... » (au moins 10 lettres ou chiffres, titre strictement plus long), puis titres complets (à chaque début de mot, le plus long qui y commence) ; enfin, une seule sélection parmi tous : le plus long dans la page l'emporte sur ceux qu'il chevauche, le tronqué à égalité, puis le plus à gauche. La recherche reste linéaire sur un long texte d'un seul bloc : normalisation par un chemin rapide pour l'ASCII, et seule la fin d'un segment, pas plus longue que le plus long titre, est examinée pour un titre tronqué. Script classique, injecté avec `contenu.js` ; il s'expose sur `globalThis.DramatoonsCorrespondance`, et les tests l'importent pour cet effet.
  - `contenu.js` : script de contenu. Il surligne les nœuds de texte de la page (sauf scripts, styles, champs de saisie, zones éditables et tout ce qui n'est pas du HTML, comme le texte d'un SVG), avec des styles `!important` pour qu'une feuille de style de la page ne les écrase pas, et sait retirer le surlignage en remettant les nœuds de texte d'origine eux-mêmes, sans fusionner leurs voisins (un framework comme React ou Vue garde des références vers ses nœuds). Une seconde injection dans la même page réutilise l'écouteur déjà en place. Une fois la page surlignée, il surveille ses modifications dans tout `<html>`, pour suivre un `<body>` remplacé en entier (`MutationObserver` : éléments ajoutés, textes modifiés sur place ; seul le texte du `<body>` est surligné), les regroupe et ne traite que les textes concernés après 300 ms sans nouvelle modification (`DELAI_MS`) ; il surveille aussi chaque nœud de texte d'origine qu'il a remplacé : si le site le modifie hors de la page (élément recyclé par un framework), il le remet à la place de son surlignage, avec sa nouvelle valeur, puis le surligne de nouveau s'il le faut. Il coupe la surveillance pendant ses propres modifications, et l'arrête au retrait du surlignage. Limites : un titre découpé entre plusieurs éléments (`<b>Solo</b> Leveling`) n'est pas reconnu ; seul le cadre principal de la page est surligné, pas ses iframes (widget de commentaires, lecteur intégré), dont le contenu vient souvent d'un autre site ; un document sans `<body>` (fichier SVG ou XML) n'est pas surligné.
  - `popup.html`, `popup.css`, `popup.mjs` : la fenêtre de l'extension. Elle vérifie l'accès à tous les sites (`chrome.permissions.contains`) et, s'il manque, propose de le demander (`chrome.permissions.request`, qui doit partir d'un clic).
- `scripts/` : `verifier.mjs` et `lint-firefox.mjs`, vérifications de la CI (voir « CI »).
- `tests/` : tests Vitest (`*.test.js`). `chrome-simule.js` remplace l'API `chrome` du navigateur (stockages en mémoire) ; les tests de la fenêtre et du script de contenu tournent dans `happy-dom`.

La construction du zip de production n'existe pas encore : elle viendra avec son propre ticket (script `build.sh`). Elle remplacera `API_URL` par l'adresse de l'API de production et retirera du manifeste l'entrée de l'API du dev (`127.0.0.1:8081`). Ce retrait nettoie le manifeste publié mais ne réduit pas les droits, déjà couverts par `<all_urls>`. D'ici là, aucun zip ne se publie depuis `src/`.

## CI
`.github/workflows/ci.yml` tourne sur chaque PR vers `main`. Deux checks, obligatoires pour fusionner, avec la relecture IA :
- **Vérifications** : `npm ci`, puis `npm run ci`, qui enchaîne :
  1. `scripts/verifier.mjs` : `manifest.json` est un JSON valide, sa version est celle de `package.json`, chaque fichier qu'il référence (icônes, fenêtre, scripts) existe, et chaque fichier JS a une syntaxe valide, selon la convention de la section « Organisation ». Le JS de `scripts/` et `tests/` est vérifié comme module. `web-ext lint` ne suit que les règles de Firefox : ce script couvre aussi ce qui ne sert qu'à Chromium ;
  2. `scripts/lint-firefox.mjs` : `web-ext lint` sur `src/`, le validateur de Mozilla, le même que celui du store. Toute erreur et tout avertissement font échouer la CI, sauf `BACKGROUND_SERVICE_WORKER_IGNORED` : Firefox ignore volontairement la clé `service_worker`, qui sert à Chrome et Edge.
- **Tests** : `npm ci`, puis `npm test`.

### Relecture IA
`.github/workflows/relecture.yml` est celui de l'API (voir « Relecture IA » dans `api/CLAUDE.md`), sur les PR vers `main` au lieu de `release/*`, avec deux différences :
- pas de PR de synchronisation : ce dépôt n'a pas de release ;
- les PR liées de l'API et du front sont cherchées vers n'importe quelle branche `release/*`, et non vers la cible de la PR relue (`main`). La release attendue est le champ Release du ticket, que le jeton du workflow ne peut pas lire : le relecteur vérifie, d'après les PR liées, que l'API et le front visent la même release. Les relectures de l'API et du front, elles, cherchent la PR de l'extension vers `main` et leurs PR liées vers leur propre release.

Le check « Relecture IA » est obligatoire pour fusionner dans `main` (ruleset), avec les deux checks de la CI.

## Git
Workflow : skill `workflow-github`. Pas de branche `release/*` : chaque branche de ticket part de `main` et y revient par PR. Une version publiée sur les stores porte le tag `vX.Y.Z`, posé sur `main` par Claude à la demande de l'utilisateur.
